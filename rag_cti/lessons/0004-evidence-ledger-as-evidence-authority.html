Lesson 04 · Evidence Ledger

Evidence Ledger：一次运行的证据权威

第四课讲 Agentic RAG 里“证据到底放在哪里”。工具可以返回摘要，prompt 可以展示片段，trace 可以记录事件，但最终答案能引用什么，必须由一个结构化、可去重、可合并、可验证的 ledger 决定。

先看全局：本课在地图哪里

前三课已经建立了控制链：入口决定 runtime path，state 记录运行过程，tool boundary 把模型 proposal 变成 observation。现在的问题是：observation 里拿到的检索结果、图查询结果、事实结果，怎样成为后续 synthesis 和 citation 能信任的证据集合？

Retrieval/Knowledge

Corpus、retriever、reranker、graph query、facts 都会产生候选知识。ledger 负责把这些候选转成一次 run 内的证据集合。

Evidence and Trust

Citation、grounding、faithfulness 都依赖 ledger 的真实 ID 集合。没有 ledger，就很难判断引用 ID 是否真实存在。

Multi-Agent

supervisor 多分支时，每个 worker 有 branch-local ledger，最后需要 merge 成 master ledger。

Cross-cutting

State vs Memory、Context vs Prompt、Provenance、Replayability 都会在 ledger 设计里显形。

本课核心胜利：你能把 ledger 从“工具结果列表”提升为“本次运行的证据权威”：它不是 prompt、不是 trace、不是长期知识库、也不是最终答案，而是 answer synthesis 和 citation validation 共同依赖的结构化事实源。

学习目标：你要能回答三件事

1

能解释 ledger 和 context、state、trace、corpus 的边界：它保存本次 run 收集到的可用证据和 provenance。

2

能说明 chunks、facts、outlines、actions 分别为什么存在，以及哪些东西能成为 citable ID。

3

能评价 ledger 是否支持去重、merge、conflict surfacing、citation guard 和 eval 所需的 evidence view。

如果我是你，我会先问什么

ledger 很容易被误解成“把工具返回值 append 到数组”。如果我站在你现在的知识状态，我会先问这四个更基础的问题：

问题概念答案为什么重要
ledger 保存的是所有知识吗？ 不是。它保存 本次运行已经收集到 的证据视图。 长期知识在 corpus/graph/fact store；ledger 是 per-run evidence authority。
模型看到的摘要就是 ledger 吗？ 不是。摘要是给模型看的 projection，ledger 保存更完整的结构化证据。 如果把摘要当 ledger，截断或格式化会影响 citation 和 eval。
为什么 action 也在 ledger 里？ action log 记录做过哪些工具调用，帮助去重、计数和审计。 action 本身不是 CTI 证据，但它解释证据是如何被收集的。
outline 算不算 citation evidence？ 通常不算。outline 更像 coverage map 或探索提示。 把 outline 当可引用证据，会让“知道应该看哪里”和“已经有证据支持 claim”混在一起。

核心概念一：ledger 是 per-run authority

“per-run” 很重要。用户问一个问题时，agent 会进行若干轮检索、图查询、事实拉取。ledger 只代表这一次运行已经收集到、可以被后续环节使用的 evidence set。它不是全局数据库，也不是长记忆。

这带来一个工程好处：最终答案的可引用范围是清楚的。模型即使知道某个 chunk id 的名字，如果这个 id 没进入本次 ledger，citation guard 也应该把它丢掉。这样可以防止模型凭空引用、引用旧 run 的证据、或者引用知识库里存在但本次没有检索到的材料。

概念判断：“知识库里存在”不等于“本次答案可以引用”。本次答案能引用什么，要看本次 ledger 的 real_id_set。

核心概念二：chunks、facts、outlines、actions 的边界

ledger 项保存什么能不能作为 citation为什么需要
chunks 检索到的文档片段，带 chunk id、source、score、text。 通常能。 回答自然语言问题时，chunk 是常见的可引用证据单位。
facts 结构化事实，带 fact id、subject、predicate、object、support。 能，前提是 fact 有真实 ID 和 support。 图/事实工具适合提供明确关系，比如某 actor 使用某 technique。
outlines 实体覆盖图、邻接关系、探索线索。 通常不能直接作为最终 claim 的 citation。 它帮助决定下一步查什么，但不是 claim proof 本身。
actions 工具调用名和紧凑参数。 不能。 它解释 agent 做过什么，支持去重、预算、tool count 和审计。

这里的关键不是字段名，而是证据类型。一个好的 ledger 不只保存“文本”，还保存 provenance、id、score、支持关系和冲突信号。这样 citation、grounding、eval 才有地方查。

具体场景：graph query 的摘要和完整证据

假设用户问某个 actor 使用了哪些 ATT&CK techniques。graph_query 可能查到很多行。为了保护 context window，模型看到的摘要会被限制；但 ledger 仍应该保存完整行或结构化 facts。这样做的意义是：

层保存什么为什么这样设计
模型可见 summary 少量 rows、简短字段、下一步提示。 控制 prompt 长度，避免一次工具结果淹没下一轮推理。
EvidenceLedger 完整结构化 rows/facts，带 id 和 provenance。 synthesis、citation guard、eval 需要完整证据权威。
Trace/Event 工具调用结果概要、状态、错误类型、delta。 让人知道发生了什么，但不把所有证据正文塞进日志。

这就是 “Context vs Ledger” 的边界：context 是当前给模型看的投影，ledger 是系统保留的证据权威。它们可以来自同一工具结果，但不能互相替代。

具体场景：多分支合并为什么需要 ledger merge

进入 supervisor 后，一个问题可能被拆成多个独立分支。例如“比较 APT29 和 Lazarus 的 technique overlap”：一个 worker 查 APT29，一个 worker 查 Lazarus，一个 worker 查 overlap 或 shared technique。每个 worker 都应该有自己的 branch-local ledger，最后合并成 master ledger。

设计点如果没有它ledger merge 应该保证什么
chunk 去重 同一 chunk 被多个分支重复引用，context 和 eval 都膨胀。 同 id 合并，保留更合理的 score 或排名信息。
fact 去重 相同 fact 重复出现，答案看似证据很多，其实重复。 按 fact id 去重，保持 provenance。
outline 合并 不同分支的 coverage map 丢失，无法解释探索范围。 按 entity/facet 保存覆盖信息。
citation guard Composer 引用分支证据时，主流程找不到 id。 最终答案的 citation validation 以 merged master ledger 为准。

常见误解

误解为什么不对更好的理解
“ledger 就是 prompt 里的 evidence section。” prompt section 是 ledger 的有限投影，可能按 top-k、token budget、fact limit 裁剪。 ledger 是结构化权威，prompt 是给模型看的当前视图。
“只要知识库里有 id，答案就能引用。” 这会绕过本次运行的 evidence gathering。 citation guard 应该看本次 ledger 的 real id set。
“outline 已经说明图里有哪些关系，所以可以当证据。” outline 常常只是 coverage 或导航结构，不一定包含支持 claim 的具体事实。 outline 帮助找证据；facts/chunks 支持 claim。
“action log 证明了答案内容。” “调用过 retrieve”不能证明某个 CTI claim 成立。 action log 证明系统做过什么；evidence 证明答案说了什么。
“ledger 越大越好。” 无边界累积会带来重复、噪声、成本和错误引用。 ledger 应该完整但有结构，synthesis 再选择相关工作集。

读代码时问什么

审计问题你在找什么
哪些工具写 ledger？ 检索、图查询、fact 查询是否都通过统一 adapter 写入，而不是散落在 prompt 文本里。
哪些 ID 是 citable？ real_id_set 是否只包含 chunk/fact 等真正证据 ID。
摘要和完整证据是否分离？ 模型看到 bounded summary，ledger 保留完整结构化结果。
去重规则是什么？ chunk、fact、outline 是否按稳定 id 合并；score 或 support 如何保留。
冲突如何表达？ conflict facts 是否被 surfaced，而不是被系统悄悄解决或忽略。
多分支怎么合并？ branch ledger merge 后，Composer 的 citation 是否能被 master ledger 验证。

本课小结

EvidenceLedger 的核心不是“保存工具结果”，而是“给一次运行建立证据权威”。chunks/facts 提供可引用证据，outlines 提供覆盖和探索线索，actions 提供运行审计。prompt 只能展示 ledger 的一部分；最终答案的 citation 必须回到 ledger 验证。下一课会在这个基础上拆 citation、grounding、faithfulness 和 sufficiency 的区别。
