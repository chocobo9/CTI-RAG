Lesson 02 · State Management

State 与 Observation：一次运行的控制记录

第二课接在 runtime harness 后面：入口已经决定了走哪条路，接下来要问的是，一次 agent run 如何知道自己刚做过什么、还缺什么、能不能继续、为什么停止。

先看全局：本课在地图哪里

整张 Agentic RAG 工程地图里，state 管理横跨“运行控制”和“证据与上下文”。这也是它容易混的原因：它既接近控制平面，又会引用证据 ledger，还会被渲染进 prompt/context 给模型看。

运行控制

iteration、tokens、stop reason、provider error、tool budget、deadline。它们回答：这次运行有没有继续的资格。

边界记录

action proposal、validation、RuntimeObservation、RuntimeEvent。它们回答：模型提出了什么，runtime 实际允许了什么。

证据权威

EvidenceLedger 保存 chunks、facts、outlines、actions 和可引用 ID。它回答：答案能引用什么证据。

模型可见上下文

每轮 prompt 里渲染的是 state/ledger 的视图，不等于 state 本身。它回答：模型这一轮需要看到哪些摘要。

本课的位置：第一课讲“谁决定 runtime path”；第二课讲“进入 single-agent gather loop 后，runtime 怎样记录过程”。如果这一层没分清，后面学 tool calling、ledger、citation、supervisor 时会把“运行记录”“证据权威”“模型上下文”混成一团。

学习目标：不是背字段

1

能解释 runtime state、memory、prompt/context、EvidenceLedger 的区别：state 管控制进度，ledger 管证据权威，context 是给模型看的当前视图。

2

能读懂一次工具边界如何从 action proposal 变成 RuntimeObservation，再经 reducer 更新 state/ledger，并形成 RuntimeEvent。

3

能评价一个 state 设计是否支持审计：是否记录无动作、拒绝、无效参数、工具错误、provider error、ledger delta 和 stop reason。

这节课的主要能力不是“知道 RuntimeInvestigationState 有哪些字段”，而是看到任何 Agentic RAG 的 run loop 时，都能判断：哪些东西是控制状态，哪些东西是证据，哪些只是模型可见文本。

如果我是你，我会先问什么

还没有系统概念时，state 很容易被理解成“agent 的记忆”。我会先问四个更工程化的问题：

问题短答案为什么重要
模型下一轮为什么不会重复做同一件事？ 不是因为模型真的记住了，而是 runtime 从 ledger/actions/observations 渲染出“已做过什么”。 这把“记忆”从模型内部移到可审计的系统记录里。
ToolMessage.content 是真相来源吗？ 不是。它是协议文本，给模型看；runtime truth 应该在结构化 observation 和 reducer 后的 state/ledger 里。 如果靠文本回放状态，截断、格式变化、并发顺序都会让系统不可复现。
没有新增 chunk/fact 就一定 no_progress 吗？ 不一定。成功 resolve entity 或 graph outline 可能是 setup progress。 否则系统会在“刚完成准备工作、还没开始拿证据”时过早停止。
为什么不把所有东西都放进 EvidenceLedger？ 因为 ledger 是证据权威，不是所有控制状态的垃圾桶。 把 provider error、stop reason、proposal validation 都塞进 ledger，会污染 citation/grounding 的概念边界。

Action Proposal 模型提出“我想调用某个工具和参数”。 它还不是执行事实，也不应该直接进入 ledger。
Validate + Execute runtime 检查工具名、参数、预算、deadline、重复调用，再决定是否执行。 它不是只靠 prompt 约束模型“不要乱来”。
RuntimeObservation 一次工具边界的收据：status、error、summary、structured payload、ledger delta、model-visible content。 它不是单纯的日志字符串，也不是 ToolMessage 本身。
Reducer 确定性地把 observation 影响应用到 state 和 EvidenceLedger。 它不让模型自由决定哪些状态被保存。
Stop Decision 根据 sufficiency、new evidence、setup progress、预算、时间、错误等决定继续或 synthesize。 它不等于模型说“我觉得够了”。

核心概念拆开看

Runtime State

一次运行的控制仪表盘。它保存 iteration、token、progress、sufficiency、stop reason、observations、events 等，让 runtime 能解释“现在走到哪一步”。

Observation

一次边界结果。它把工具成功、工具错误、无效调用、拒绝调用、无动作、provider error 都统一成结构化记录。

Event

从 observation 派生出的 trace-friendly envelope。它更适合统计和观测，例如 tool_result、invalid_tool_call、provider_error。

Reducer

确定性合并器。它决定 observation 怎样改变 state 和 ledger，所以它是可复现、可测试、可审计的关键边界。

EvidenceLedger

证据权威。它保存完整 chunks/facts/outlines/actions 和真实可引用 ID，不是 provider 状态、prompt 文本或全部运行日志。

Working-Set Context

每轮重新构造给模型看的工作视图：已经收集了什么、已做过哪些 action、还缺什么。它是 state/ledger 的投影，不是长期记忆本体。

状态边界：六个东西别混

读 Agentic RAG 代码时，最有用的不是问“这个变量叫什么”，而是问：它承载的是能力、过程、证据、模型输入、观测事件，还是最终输出？

对象应该保存什么不应该保存什么CTI-RAG 例子
RuntimeDeps 可复用服务和 provider policy。 本次运行的 reasoning state。 settings、retriever、fact_store、models、judge、composer。
RuntimeInvestigationState 本次运行的控制变量和边界记录。 长期记忆、共享缓存、可复用 provider client。 iteration_count、tokens_used、sufficiency、stop_reason、observations。
RuntimeObservation 某个 action/tool boundary 的结构化结果。 最终答案、全局路线选择。 status、tool_name、ledger_delta、structured_payload、model_visible_content。
RuntimeEvent 可统计、可 trace 的事件摘要。 完整证据正文。 tool_result、tool_error、invalid_tool_call、no_tool_call。
EvidenceLedger 本次运行收集到的证据权威。 provider error、route decision、prompt transcript。 chunks、facts、outlines、actions、real_id_set。
Prompt / Context 给模型看的当前工作视图。 系统的唯一状态源。 render_state_view、render_action_log、resolved entity setup state。

一个具体例子：为什么 setup progress 不是 evidence

假设用户问：“APT29 和 Lazarus Group 共同使用了哪些 techniques？”模型第一轮可能先调用 resolve_entity，把 APT29/Lazarus 映射到 graph entity id。这个动作没有新增 chunk，也没有新增 fact，所以 new_evidence = 0。

但这不代表它毫无进展。它完成的是 setup progress：后续 graph_outline 或 graph_query 需要这些 entity id 才能拿到真正证据。如果 runtime 只看 new_evidence == 0，它会误判 no_progress，刚热身就宣布结束。

阶段发生了什么应该进入哪里为什么
Turn 1 resolve_entity(name=APT29) 成功。 RuntimeObservation.structured_payload + state observations。 这是未来工具调用需要的 setup state，不是可引用证据。
Reducer 记录 observation/event，计算 setup progress。 RuntimeInvestigationState。 stop policy 需要知道这轮虽然没拿证据，但仍然推进了任务。
Turn 2 runtime 渲染 resolved entity state 给模型。 Prompt/context。 模型看到 entity id 后，才能继续 graph_outline 或 graph_query。
后续证据 graph_query 或 retrieve 拿到 facts/chunks。 EvidenceLedger。 这些才可能成为 citation/grounding 的证据来源。

概念重点：setup state 可以帮助系统继续工作，但它不等于 evidence。把它和 evidence 分开，stop policy 才不会过早停止，citation guard 也不会把不可引用的准备信息当成证据。

常见误解

误解更准确的理解
State 就是 agent 的长期记忆。 不是。这里的 state 是一次 run 的控制状态。长期知识在语料库、索引、图数据库或外部 memory 系统里；本课讲的是运行中的短期控制记录。
只要 prompt 里有历史，系统就有状态。 prompt 历史是模型输入，不是可靠状态源。可靠状态要能被代码读取、测试、回放、统计。
Observation 就是 ToolMessage。 不是。ToolMessage 是 provider 协议文本；Observation 是 runtime 自己的结构化边界结果。前者给模型看，后者给系统审计和 reducer 使用。
EvidenceLedger 可以保存所有运行过程。 不该这样。ledger 是证据权威，尤其服务 citation/grounding；控制状态、错误、proposal validation 应该有自己的 state/event 边界。
new_evidence 为 0 就应该停。 要看是否有 setup progress、是否还有明确 gap、是否预算耗尽。resolve_entity 这类准备动作可能不产生 citation evidence，但仍能推进任务。

读代码时的审查清单

这不是背诵口号，而是一组架构判断问题。以后看任何 Agentic RAG state 设计，都可以沿着这组问题审：

检查点为什么重要危险信号
Per-run state 是否和 RuntimeDeps 分离？ 一次运行的状态不能污染可复用服务。 deps 里出现 branch reports、ledgers、final answer。
工具边界是否产生结构化 observation？ 只有结构化结果才能被 reducer、trace、tests 稳定消费。 只把工具输出拼成字符串塞回模型。
reducer 是否拥有 state/ledger mutation？ 这决定系统能否回放和审计。 工具函数到处直接修改 ledger，外层 state 只能猜 delta。
状态是否区分 invalid、rejected、error、no_action？ 这些结果对调试、eval、stop policy 的含义完全不同。 所有失败都叫 exception 或空结果。
stop policy 是否基于结构化信号？ 停止原因需要能被解释和测试。 模型说“够了”就直接 synthesize。
model-visible content 是否只是投影？ 模型可见文本会被截断或重写，不能成为唯一 truth。 系统从显示摘要里 parse 回关键状态。
