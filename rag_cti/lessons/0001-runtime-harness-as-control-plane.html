Lesson 0001

Runtime Harness 是控制平面

本课先建立一个概念判断：runtime harness 是 agent 外部的控制平面。CTI-RAG 的 answer() 只是这个概念在项目里的例子，用来帮助你看见边界，而不是要你从函数实现开始背架构。

先看全局：这张图有多大

你现在的起点不是“不懂某个函数”，而是还没有一张系统地图。整张 Agentic RAG 工程地图大约包含 10 类、86 个概念节点。第一课只拿其中最靠前的一层：runtime harness，也就是让 agent 运行起来但不失控的控制平面。

输入与路由

Query understanding、query rewrite、intent classification、routing policy、supervisor admission。它们回答：用户到底要什么，应该走哪条路。

运行控制

Runtime harness、state、action proposal、tool validation、observation、reducer、stop policy、budget。它们回答：agent 每一步能做什么，何时停止。

证据与上下文

Corpus、indexes、retriever、graph query、evidence ledger、provenance、context window、working memory。它们回答：证据从哪里来，如何被保存和送进模型。

可信度与质量

Citation、grounding、faithfulness、supervisor、composer、eval、observability、deployment。它们回答：答案凭什么可信，系统如何被评价和运维。

本课的位置：我们从“运行控制”开始，不是因为它最重要，而是因为它是读后面所有层的坐标系。你先知道谁负责控制、谁负责证据、谁负责合成，后面读 ledger、supervisor、citation/eval 才不会混在一起。

学习目标：概念优先

1

能用自己的话说明 runtime harness 控制什么、不控制什么：它管入口、路由、工具边界、预算、停止和 trace；它不负责直接“拥有”所有知识。

2

能区分能力、运行过程、证据权威：依赖是系统能用什么，state 是这次运行发生到哪里，ledger 是本次答案能引用什么。

3

能判断什么时候应该保守退回 single-agent：理解失败、分支不独立、只是检索提示、或任务不需要并行合成时，不应放行 supervisor。

本课如何使用代码：代码是例子，不是主体。我们用 CTI-RAG 的对象名和入口函数给概念找落点；真正要掌握的是边界判断，而不是记住某个函数在哪一行。

如果我是你，我会先问什么

假设我现在还没有 Agentic RAG 的系统地图，我不会先问“answer() 里每一行在做什么”。我会先问下面四个问题，因为它们决定我能不能把后面的术语放到正确位置：

先问的问题为什么它是第一课的问题
一个用户问题进入系统后，谁负责决定下一步？ 这就是 runtime harness / control plane 的问题。先搞清“谁控制”，再看“谁执行”。
系统什么时候应该相信模型，什么时候必须用代码挡住？ Agentic RAG 的风险来自模型会提议行动；runtime guardrails 负责把提议变成可控行动。
证据、状态、记忆、上下文是不是一回事？ 不是。后面所有 citation、grounding、eval 都依赖这些边界。混了就很难判断答案是否可信。
复杂问题是不是都应该多 agent？ 不是。Supervisor 只适合独立分支并行收集后再合成；复杂但顺序依赖的问题可能更适合 single-agent。

所以第一课不是教一套实现细节，而是教你建立四个槽位：控制、执行、证据、合成。后面每个新术语都先放进这四个槽位里。

这张图在讲什么

这张图不是在说“代码按这 5 个函数顺序执行”。它讲的是 runtime harness 把一个不确定的用户请求逐步变成可执行、可审计路径 的过程。你可以把它理解成一个决策漏斗：越往右，系统越知道自己要做什么、允许谁做、依据什么证据停下来。

格子它在概念上做什么它不是在做什么
User Query 保留用户原始问题和对话历史。这里的信息通常是模糊、口语化、上下文依赖的。 它还不是检索查询，也不是可执行计划。
Query Understanding 把原始问题整理成系统能操作的任务视图：独立问题、实体、约束、检索提示，以及可能的分解建议。 它不是直接查证据，也不是最终决定 supervisor 一定能跑。
Admission 控制平面做保守裁决：这个任务是否真的适合多分支并行？如果不适合，就退回 single-agent。 它不是质量评测，也不是答案生成；它只决定运行拓扑。
Gather Evidence 被选中的路径开始调用工具：检索、图查询、实体解析等。工具结果写入 evidence ledger。 它不是自由聊天，也不应该绕过工具验证和预算。
Synthesize + Guard 基于 ledger 里的证据生成答案，并做 citation validation、stop reason、trace 等收尾。 它不是重新收集证据；它应该在稳定的证据集合上合成。

为什么第一课先看前三格：前三格决定“任务形状”和“运行路径”。如果你还没分清 query understanding、retrieval query、decomposition proposal、supervisor admission，后面看 ledger、worker、Composer、citation guard 时会一直混：到底是谁在理解问题，谁在查证据，谁在决定并行，谁在合成答案。

三个例子：同样是 CTI 问题，路径可能不同

runtime harness 不是看到 CTI 问题就机械套同一条工作流。它要先判断任务形状，再选择路径。

用户问题任务形状可能路径为什么
APT29 使用了哪些 ATT&CK techniques？ 单实体枚举 Single-agent 通常只需要围绕一个实体收集证据。没有天然需要多个独立 worker 并行合成。
比较 APT29 和 Turla 的 techniques，有哪些相同和不同？ 可并行比较 可能进入 Supervisor APT29 和 Turla 可以分别收集证据，再由 Composer 合并比较。前提是分支独立、数量合理、需要最终合成。
先根据这组 infrastructure 找可能 actor，再解释该 actor 的 TTP。 顺序依赖 Single-agent 或更保守路径 第二步依赖第一步发现。强行拆成并行 worker 会让后续分支缺少必要输入。

Supervisor 的定位：概念 vs CTI-RAG 当前实现

先把最容易混的地方说清楚：supervisor 不是“更聪明的回答者”，也不是生产入口的总路由器。在 Agentic RAG 里，它的概念定位是一个多分支协调层：当任务已经被判断为适合拆成多个独立分支时，它负责让不同 worker 去收集证据，然后把这些分支结果交给 Composer 合成。

一句话版本：runtime harness 决定要不要进入 supervisor path；supervisor 协调 worker；worker 收集证据；Composer 写最终答案；citation guard 校验引用是否真的来自 ledger。

角色它负责什么它不负责什么
Runtime harness 理解任务形状，做 supervisor admission，选择 single-agent path 或 supervisor path。 不亲自替每个分支收集证据，也不把所有复杂问题都交给 supervisor。
Supervisor 接受已放行的 branch plan，调度 gather-only workers，汇总 branch reports，触发 Composer。 不直接 retrieve，不写最终答案，不做 citation validation。
Worker 围绕一个 sub-question 收集证据，维护 branch-local ledger，产出 BranchReport。 不协调其他分支，不写全局最终答案。
Composer 基于 branch reports 和已接受的证据上下文写一个最终答案。 不再查证据，不新建分支，不修 citation。
Citation guard 用合并后的 master ledger 校验答案里的引用 ID 是否真实存在。 不负责重新生成答案，也不证明每个自然语言 claim 都完全 faithful。

为什么你会觉得 supervisor 模糊

因为“supervisor”这个词在很多 agent 框架里听起来像一个老板：它似乎应该理解问题、拆任务、调工具、看结果、写答案。但 CTI-RAG 的目标设计更保守：把“能不能走 supervisor”放在 runtime harness 里，把“分支协调”留给 supervisor。这样做的好处是，生产入口有一个稳定的 admission 门，不会让一个 LLM 在运行中随意把普通搜索子查询变成多 agent fan-out。

CTI-RAG 里的形态代码路径你应该怎么理解
生产路径：validated branch plan answer() → evaluate_supervisor_admission() → run_supervised_answer(branch_plan=...) answer() 先决定是否放行；进入后按已验证分支确定性 dispatch workers。这里 supervisor 不是重新做路由判断。
调试/评测路径：legacy autonomous supervisor supervised_answer() 或 run_supervised_answer(branch_plan=None) 保留一个 ReAct-style supervisor，让它通过 dispatch_worker 和 compose_answer 工具协调流程。它适合 baseline、debug、eval，不应被误认为生产主入口。

所以读这个项目时，你可以把 supervisor 放在一个很窄但重要的位置：它不是“是否使用多 agent”的裁判；它是“多 agent 已被允许以后，如何把分支工作组织起来”的协调者。

本课的核心概念拆开看

Runtime Harness

它是模型外面的运行环境。模型可以提出下一步，但 harness 决定这个下一步能不能执行、由哪个工具执行、执行结果如何进入 state、什么时候停止。

Control Plane

控制平面关心“允许什么发生”。它管理入口、路由、验证、预算、deadline、stop policy、trace。它不直接等同于检索、图数据库或知识库。

Data Plane

数据平面关心“证据从哪里来”。语料、chunk、vector/BM25 index、fact store、graph query、retriever 都偏数据平面。

Admission

Admission 是从“模型建议”到“系统放行”的门。它不问答案对不对，而是问这个运行拓扑是否安全、清楚、可控。

这四个概念合在一起，就是第一课要建立的坐标：用户请求进入系统以后，先被控制平面塑形；证据收集和答案生成只是被塑形后的执行阶段。

常见误解

误解更准确的理解
Runtime harness 就是一条固定 workflow。 不是。workflow 是预先写死路线；runtime harness 是给 agentic 行为加边界。它允许模型或系统选择路径，但选择必须被 state、工具验证、预算和 stop policy 约束。
Query understanding 就是把问题改写成搜索词。 不止。搜索词只是 retrieval hints。runtime 级理解还要保留任务意图、实体、约束、历史消解、是否可能分解，以及解析失败时的 fallback 状态。
Supervisor 就是更强的 agent，所以复杂问题都应该走 supervisor。 不是。Supervisor 适合独立分支并行 gather 后再合成。复杂但顺序依赖的问题，或者需要共享探索 ledger 的问题，反而不适合简单 fan-out。
有 citation 就说明答案可信。 不够。citation valid 只说明引用 ID 存在于 ledger；grounding 说明答案基于证据；faithfulness 才问每个 claim 是否真的被证据支持。后两者会在第 5 课展开。

核心解释

控制平面不是“做所有事”的地方。 它负责决定什么可以发生、什么时候停止、如何记录发生过什么。真正拿证据的是工具和检索/图查询；真正保存证据的是 ledger；真正合成答案的是 generator 或 Composer。

RuntimeQueryUnderstanding 比 query rewrite 高一层。 它包含 standalone query、retrieval queries、entities、payload constraint、decomposition、status 和 confidence。retrieval queries 只是搜索提示；decomposition 才可能进入 supervisor admission。

Supervisor admission 必须保守。 进入 supervisor 意味着并发 worker、分支 ledger、Composer、更多 provider 调用和更复杂的 citation guard。如果分支不独立，或者只是搜索子查询，就应该回到 single-agent path。

这里真正要学的概念：运行时对象的责任边界

这一组词不是为了背代码名，而是为了建立一个判断：同一次 agent run 里，能力、过程、证据、边界结果不能混在一起。混在一起以后，系统就很难并发、复现、审计，也很难判断一个答案到底基于什么。

对象它回答的问题为什么要单独分出来
Deps 这次运行可以使用哪些能力？例如模型、retriever、fact store、judge、composer。 能力应该可复用、可注入、可替换；它不应该携带某一次问题的中间推理历史。
State 这次运行已经走到哪里？例如轮数、预算、当前 gap、stop reason。 控制平面需要它来决定下一步：继续 gather、停止、降级、还是合成。
Ledger 这次运行真正收集到了哪些证据？哪些 chunk/fact 可以被引用？ 答案可信度必须回到证据权威，而不是回到模型 transcript 或一段摘要。
Observation 一次工具边界之后发生了什么？成功、失败、被拒绝、增加了哪些证据？ 模型提出 action 还不是事实；只有 observation 才能被 reducer 合并进 state 和 ledger。

所以这不是口诀，而是边界检查：看到一个字段或对象时，先问它属于“能力”“运行过程”“证据权威”还是“工具边界结果”。如果一个对象同时承担太多类职责，它通常会让 runtime harness 变得难测、难审计、难复现。

练习：控制平面判断

目标不是背术语，而是看到一段设计或代码时能立刻判断：它属于入口、状态、工具边界、证据权威，还是质量 guard。

1. answer() 在第一课里应该被当成什么？

2. “APT29 techniques”和“Turla techniques”这类搜索词首先是什么？

3. RuntimeDeps 应该保存哪类东西？

4. iteration、tokens、stop reason 属于哪类东西？

5. query understanding 解析失败时，supervisor admission 应该怎么做？

6. 分支之间有顺序依赖时，应该走哪条路径？

7. 工具参数缺失或类型错误，应优先在哪一层挡住？

8. 工具执行后的 status、error、ledger_delta 叫什么？

9. 最终合成和 citation guard 应该相信什么？

10. 引用 ID 是否存在于 ledger，优先由谁判断？

11. sufficiency 认为证据不足且还有明确 gap 时，下一步通常是什么？

12. Composer 在 supervisor path 里主要是什么角色？
