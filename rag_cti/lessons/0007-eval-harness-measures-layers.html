Lesson 07 · Evaluation

Eval Harness：先说明你在测哪一层

第七课讲 Agentic RAG 的评价。不要一上来问“RAGAS 分数多少”。更工程化的问题是：这个 eval 测的是 retriever 候选、agent 收集到的 evidence、最终答案、citation、faithfulness、成本，还是一次代码变更的回归风险？

先看全局：本课在地图哪里

前面我们建立了 runtime、state、tool、ledger、grounding、supervisor。eval harness 要把这些运行层拆成可测对象。一个单分数不能覆盖整个系统，因为每层失败的原因不同，修复方向也不同。

Retrieval Eval

测 retriever 是否把 gold evidence 放进 top-k。关注 hit@k、MRR、NDCG、category breakdown。

Gathered Evidence Eval

测 agent 工具路径最终收集到的 ledger 是否覆盖问题，而不只看最初检索器。

Answer Eval

测最终 response 是否 relevant、complete、structured，是否回答了用户问题。

Trust Eval

测 faithfulness、citation validity、grounding、conflict handling，避免“看起来像答案”但证据不稳。

本课核心胜利：你能评价任何 CTI-RAG eval 设计时先问“它测的是哪一层的失败模式”。如果一个分数没说明层级，你就不能知道该修 retriever、工具路径、ledger、prompt、composer、citation guard 还是 runtime policy。

学习目标：把 eval 从分数变成诊断

1

能区分 retrieval eval、gathered evidence eval、answer eval、faithfulness/citation eval、latency/cost eval。

2

能解释 hit@k、MRR、context precision/recall、faithfulness、answer relevancy 各自不能证明什么。

3

能读懂 CTI-RAG 的 eval 代码，把 dataset、gold ids、answer objects、RAGAS dataset 和 regression tests 对上。

如果我是你，我会先问什么

很多 eval 文档会直接堆指标。我会先从故障诊断角度问：

问题为什么先问它例子
这个 eval 的输入是什么？ 输入决定测量对象。 输入是 raw retriever results，还是 final AgenticAnswer？
gold/reference 是什么？ 没有 gold，就只能做 judge/heuristic，不能算某些确定性指标。 gold attack id、expected chunk ids、reference answer。
指标失败时能定位到哪层吗？ eval 的价值在于诊断和回归，不只是排名。 retrieval hit@k 低，可能是 index/retriever 问题；citation invalid 是 guard/synthesis 问题。
它测的是本次 run 还是离线组件？ Agentic RAG 的工具路径会改变最终 evidence。 retriever 离线 top-k 好，不代表 agent 真的调用了正确工具。

核心概念一：retrieval eval 是必要的底座

retrieval eval 直接测“候选证据有没有被找回来”。如果 gold evidence 连 top-k 都进不了，后续 agent 再聪明也很难稳定回答。CTI 场景里，gold 可能是 ATT&CK technique id、expected chunk id、source + attack id 的模糊匹配等。

指标它问什么它不问什么
hit@k top-k 中是否命中 gold。 不关心 gold 排第几之后的细节，也不关心答案。
MRR 第一个正确结果排得有多靠前。 不评估多个正确证据是否都被覆盖。
NDCG 排序质量，尤其是多相关等级时。 不直接证明最终 synthesis faithful。
Category metrics 不同问题类别上的表现差异。 不自动解释原因，需要结合数据和 trace。

retrieval eval 是底座，但不是整栋楼。Agentic RAG 的后续工具选择、branching、ledger merge、citation guard 都可能让最终表现好于或差于 raw retriever。

核心概念二：gathered evidence eval 测 agent 是否把证据真的拿到手

Agentic RAG 不只是一次 retriever top-k。它可能先 resolve entity，再 graph outline，再 facts_for_evidence，再 retrieve 补充文本。所以 eval 需要一层专门问：最终 ledger 是否有足够证据？

信号代表什么失败时可能修哪里
ledger contains gold id agent path 最终收集到 gold evidence。 tool routing、query rewrite、graph target selection。
coverage gaps sufficiency judge 认为仍缺 facet。 branch plan、next action policy、stop policy。
tool_call_count 达到答案用了多少工具动作。 预算、重复调用、routing efficiency。
stop_reason 为什么停止。 no_progress、budget、timeout、sufficient 的阈值。
branch statuses supervisor 分支是否 partial/empty/failed。 branch planning、worker robustness、merge behavior。

核心概念三：RAGAS 类 eval 测的是答案与 context 的关系

RAGAS 这类 eval 通常需要把最终 answer 转成 dataset：用户问题、retrieved contexts、response，有 reference 时再加 reference。CTI-RAG 的 answers_to_ragas_dataset 就是把 AgenticAnswer 中的 query、query_result results、response 转成这样的结构。

字段来自哪里概念意义
user_input 原始 query。 answer relevancy 要知道用户问什么。
retrieved_contexts answer 的 query_result / ledger-derived contexts。 faithfulness 和 context metrics 需要证据上下文。
response 最终答案文本。 judge 比较 response 与 query/context/reference。
reference 可选 gold answer。 有 reference 时可以测更强的 correctness/recall；没有时只能做无参考指标。

这里要小心：RAGAS 分数也不是“真理”。如果 retrieved_contexts 本身错了，faithfulness 高可能只说明答案忠实于错误 context；如果 reference 缺失，context recall 这类指标就不能正常解释。

CTI-RAG 里的代码映射

代码位置概念职责读的时候重点问什么
evaluation/retrieval_metrics.py::hit_at_k 检查 top-k 是否命中 gold attack id 或相关 id。 gold matching 是 exact、parent/subtechnique，还是 fuzzy？
reciprocal_rank 第一个正确结果越靠前，分数越高。 多个 gold 时怎么处理？没有命中如何返回？
evaluate_retriever 离线评估 retriever 在 dataset 上的 top-k 表现。 dataset 是否代表真实 CTI 问题分布？
QuerySetRecord / QuerySetEvalResult 按 category、expected chunk ids、semantic/fuzzy 规则评估 query set。 是否能定位某类 query 退化？
evaluation/ragas_eval.py::answers_to_ragas_dataset 把 AgenticAnswer 转成 RAGAS dataset。 contexts 是否来自 answer.query_result？空 contexts 如何处理？
RagasEvalResult 保存 faithfulness、answer relevancy、context precision/recall、per-query、config。 reference 缺失时默认值如何解释？
tests/unit/test_retrieval_metrics.py 验证 retrieval metrics 行为。 测试覆盖 hit/mrr/category/per_query，而不是最终答案质量。
tests/unit/test_ragas_eval.py 验证 answer 到 RAGAS dataset 的转换。 测试证明数据格式正确，不证明 judge 分数一定可靠。

具体场景：retrieval 分数高，但最终答案差

假设离线 retriever hit@5 很高，gold chunk 总能进入 top-5。但 agent 最终答案仍然错。可能原因包括：

层可能失败你该看什么
Tool routing agent 没有调用 retrieve，或过早走了错误 graph path。 RuntimeEvents、tool_call_count、observations。
Ledger 工具返回了结果，但没有正确进入 ledger。 ledger delta、real_id_set、query_result union。
Context assembly gold chunk 在 ledger，但没进入 synthesis context。 top-k selection、fact_limit、context budget。
Synthesis 模型看到了证据，但写错或夸大。 faithfulness eval、claim-level review。
Citation 答案引用错误 ID 或漏引关键 ID。 citation guard、dropped_citation_count、cited_ids。

所以 eval harness 应该能沿着 trace 定位，而不是只报告“总体分数下降”。

具体场景：RAGAS faithfulness 高，也不代表产品可用

如果答案严格复述 retrieved contexts，faithfulness 可能高。但用户体验仍可能差：

问题为什么 faithfulness 不足以发现需要补什么 eval
证据没覆盖用户关键 facet。 答案忠实于不完整 contexts。 sufficiency / coverage eval。
答案没有回答用户实际 intent。 faithfulness 不一定看 task success。 answer relevancy、task-specific rubric。
引用格式或 ID 错误。 faithfulness judge 未必检查 deterministic id validity。 citation guard metrics。
延迟和成本太高。 语义质量分不测 ops。 latency、token、tool count budgets。

常见误解

误解为什么不对更好的理解
“一个 RAGAS 分数就能代表系统好坏。” 它只覆盖特定 answer/context 关系，不覆盖所有 runtime、retrieval、ops 风险。 用分层 eval 矩阵。
“retrieval hit@k 高，答案就会好。” agent 可能没使用正确证据，或 synthesis 出错。 retrieval 是底座，不是最终质量。
“没有 reference 就不能 eval。” 不能做某些 reference-based 指标，但仍可做 citation validity、faithfulness judge、latency、regression。 区分 reference-based、reference-free、deterministic checks。
“eval 只给模型质量用。” 很多退化来自 tool boundary、state、ledger、branching、context assembly。 eval 要覆盖系统层，不只模型层。
“unit tests 和 eval 是一回事。” unit tests 验证确定性契约，eval 测数据分布上的质量表现。 两者互补：contract tests 防回归，eval 发现质量变化。

读代码时问什么

审计问题你在找什么
这个 eval 的 unit of analysis 是什么？ query、retriever result、AgenticAnswer、branch report、trace 还是 whole run。
gold labels 怎么定义？ attack id、chunk id、semantic expected ids、reference answer 是否清晰。
指标失败能定位到哪层？ 是否能从 per-query、category、trace metadata 看到 failure source。
deterministic checks 和 judge checks 是否分开？ ID validity、schema、budgets 用代码；faithfulness/coverage 用 judge 或人工 rubric。
eval 是否记录 config？ 模型、retriever、top-k、threshold、dataset version、timestamp。
是否有 regression/golden set？ 架构改动后，核心行为是否能自动发现退化。

本课小结

Agentic RAG eval 的第一原则是先说明测量层。retrieval eval 测候选证据召回，gathered evidence eval 测 agent 是否把证据收进 ledger，answer eval 测响应任务质量，faithfulness/citation eval 测证据忠实和引用真实性，ops/regression eval 测成本、延迟和稳定性。最后一课会把全课程合起来，学习如何从架构评价角度审 CTI-RAG 的 runtime contract、代码证据、测试证据和残余风险。
