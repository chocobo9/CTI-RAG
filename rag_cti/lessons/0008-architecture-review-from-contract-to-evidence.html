Lesson 08 · Architecture Review

Architecture Review：从设计合同读到证据

最后一课把前七课合起来：你要学会评价 CTI-RAG，不是只看某个函数写得好不好，而是看 runtime contract 是否清楚、代码是否守住边界、测试和 eval 是否证明关键行为、trace 是否能解释失败、残余风险是否被诚实暴露。

先看全局：本课在地图哪里

这节课对应思维导图里的 Product/Ops 和 Cross-cutting 区域，也回到整个 Agentic RAG 系统。现在你已经知道 runtime harness、state、tool boundary、ledger、citation、supervisor、eval 各自是什么；最后要练的是架构评价：这些概念在一个真实项目里是否对齐。

Design Intent

ADR、phase control doc、public API 说明系统想成为什么样。

Runtime Contract

入口、path selection、state、tool boundary、ledger、stop policy、trace 是系统对调用方的承诺。

Implementation Evidence

代码是否真的把模型 proposal、runtime observation、evidence authority、composer/citation guard 分开。

Verification Evidence

unit tests、integration tests、eval、golden sets、trace 是否覆盖关键风险。

本课核心胜利：你能拿一套明确 rubric 评价 CTI-RAG：不是“我感觉架构不错”，而是“入口合同清楚吗？状态权威在哪？工具边界硬吗？证据链闭合吗？supervisor 是否越权？eval 是否分层？trace 是否能诊断？”

学习目标：从读懂到评价

1

能把 ADR/设计文档中的 intent 映射到 runtime harness、state、tool、ledger、supervisor 和 eval 代码。

2

能用 contract-first 方法检查边界是否深：公开 API 简洁，内部运行细节完整可追踪。

3

能写出一份架构评价：strengths、evidence、gaps、tests/eval coverage、residual risks、next improvements。

如果我是你，我会先问什么

评价一个 Agentic RAG 项目时，我不会先从“这个类写得优雅吗”开始。我会先问这五个问题：

问题为什么重要CTI-RAG 里看哪里
公开 API 承诺什么？ 外部调用方应该面对稳定、简单的入口，而不是内部模式泄漏。 __init__.py、ADR 中的 answer() contract。
runtime truth 在哪里？ 如果 truth 藏在 prompt transcript 或模型文本里，系统不可审计。 runtime state、observations、events、ledger、trace。
模型能否越过边界？ Agentic 系统最怕 probabilistic proposal 直接变成 action 或 evidence。 tool validation、execution boundary、citation guard。
复杂路径是否被限制？ supervisor、多分支、parallel dispatch 都需要入场条件和 fallback。 supervisor admission、validated branch plan、legacy metadata。
失败是否可诊断？ 没有 trace 和分层 eval，质量下降时不知道修哪层。 trace metadata、stop reason、events、eval metrics、tests。

Rubric 一：Public API 与 runtime contract

好的 Agentic RAG 架构应该对外简单、对内可追踪。调用方不应该被迫理解 single vs supervisor 的内部细节，但 trace 又要能说明系统为什么选择某条路。

检查项好设计的信号危险信号
Production entry answer() 是主入口，内部决定 path。 调用方必须手动选 single/supervisor 才能正常使用。
Debug/baseline modes force single/supervisor 明确标成 debug/eval/baseline。 debug path 与 production path 混用，trace 不可区分。
Stable output shape single 和 supervised 返回兼容 shape，含 citations、trace、telemetry。 不同 path 输出字段差异大，调用方很难处理。
Fallback reasons supervisor disabled、low confidence、dependent chain 等原因进入 trace。 系统 silently fallback，无法评估 admission policy。
RuntimeDeps 保存可复用 services/policy，不保存 per-run state。 依赖和运行状态混在一起，影响并发和复现。

Rubric 二：state、tool、ledger 的权威边界

这一组检查来自前四课。它决定系统是否可审计。

边界应该成立的 contract代码证据
State per-run control state 记录进度、observations、events、stop reason。 RuntimeInvestigationState、RuntimeObservation、RuntimeEvent。
Tool boundary 模型 proposal 必须经过 validation、normalization、budget、deadline、policy。 _validate_runtime_tool_args、_execute_action_proposal。
Observation 工具结果以结构化 observation 进入 reducer，不从 ToolMessage 文本反推 truth。 runtime_harness tests around replay and ToolMessage boundary。
Ledger 本次 run 的 evidence authority，保存 chunks/facts/outlines/actions。 EvidenceLedger、real_id_set、merge tests。
Context prompt 是 state/ledger 的 working-set projection。 rendered action log、bounded evidence view、synthesis top-k。

Rubric 三：trust gates 与 supervisor

这一组检查来自第五、六课。它决定系统在复杂问题上是否仍然保持证据链闭合。

检查项好设计的信号危险信号
Citation guard 引用 ID 与 merged ledger real_id_set 做确定性检查。 只要求模型“请不要编 citation”。
Grounding/Faithfulness 明确承认 deterministic guard 不等于 claim-level support。 把 dropped citation count 当总质量分。
Sufficiency judge 给 coverage gaps 和 next_action，runtime 结合 stop policy。 模型一句“够了”直接停止，不看预算/进度/轮数。
Supervisor admission 只对 independent gatherable branches 进入 supervisor，并有 fallback reason。 复杂问题一律多 agent。
Composer no-tool synthesis，基于 branch reports 和 merged ledger。 Composer 再检索或引入新证据。
Branch failure partial/empty/failed surfaced 给 report、trace 和 final gaps。 失败分支被静默吞掉。

Rubric 四：tests、eval、observability

架构不是写在 ADR 里就算完成，必须有验证证据。

验证层应该覆盖什么CTI-RAG 例子
Unit/contract tests tool validation、invalid/rejected/error、ledger merge、citation guard、supervisor entrypoint。 test_runtime_harness.py、test_evidence_ledger.py、test_supervisor_graph.py。
Harness-level tests query-understanding fallback、valid branches admitted、dependent decomposition fallback、public answer shape。 ADR 里列出的 runtime harness tests。
Retrieval eval top-k、MRR、category/per-query metrics。 retrieval_metrics.py。
Answer/faithfulness eval RAGAS dataset conversion、faithfulness、answer relevancy、contexts。 ragas_eval.py。
Trace/observability path selected、admission reason、branch statuses、stop reason、tool counts、citation drops。 observability/tracing.py and trace metadata tests。
Regression/golden set 核心 CTI questions 在 code/model/prompt 改动后保持行为。 dataset version、config、per-query reports。

如何写一份架构评价

下面这个结构可以直接作为你以后 review CTI-RAG 的模板：

章节要写什么注意
1. Scope 本次评价覆盖 runtime harness、state、tools、ledger、supervisor、citation/eval 哪些部分。 不要把没读过的区域写成结论。
2. Intended architecture 从 ADR/docs 摘出设计意图和生产路径。 区分 production、debug、legacy。
3. Runtime contract 入口、输出、trace、state、ledger、stop reason 对调用方和维护者承诺什么。 contract 要可观察。
4. Code evidence 列出关键实现点如何支撑或违背 contract。 引用具体文件/函数，而不是泛泛夸赞。
5. Verification 哪些 tests/eval 覆盖关键行为，哪些还缺。 把 deterministic tests 和 quality eval 分开。
6. Risks and next steps 残余风险、优先级、建议补的 tests/eval/docs。 风险要可行动，不要写空话。

常见误解

误解为什么不对更好的理解
“架构评价就是看代码是否整洁。” 整洁很重要，但 Agentic RAG 的核心风险在边界、证据链、可诊断性。 用 contract + evidence + verification 的框架。
“ADR 写了就代表实现了。” 设计意图需要代码和测试证据支撑。 每条 design claim 都要找 implementation/test anchor。
“测试多就够。” 测试可能只覆盖数据结构，不覆盖 runtime contract 或质量表现。 看测试是否覆盖关键 failure modes。
“eval 高就说明架构好。” 分数高可能来自数据集窄、judge 偏差或未测 ops 风险。 分层 eval + trace + residual risk 一起看。
“supervisor 很强，所以系统一定高级。” 复杂机制如果没有 admission 和 boundary，反而更不可控。 看 supervisor 是否被限制在协调职责内。

读代码时问什么

审计问题你在找什么
这段代码属于 control plane 还是 data plane？ runtime decision、state、policy vs evidence content、retrieval result。
这里的 truth source 是什么？ state、observation、ledger、trace、prompt 之间有没有混乱。
模型输出在哪里被降级成 proposal？ tool call、sufficiency suggestion、citation text 是否经过 runtime guard。
失败是否有 typed reason？ invalid/rejected/error、stop_reason、fallback_reason、branch status。
证据链是否闭合？ tool result -> ledger -> synthesis context -> citation guard -> final answer。
测试是否证明 contract？ 有没有覆盖边界，而不是只测 happy path。

练习：做一次小型架构 review

1. 架构评价的第一步更应该看什么？

2. Public API 好设计的信号是什么？

3. RuntimeDeps 里混入 per-run state 的风险是什么？

4. “模型建议 stop”在 contract-first 视角下是什么？

5. 证据链闭合需要哪条路径成立？

6. 看到 legacy autonomous supervisor 代码时，评价时应该怎么做？

7. 测试覆盖多但仍可能有风险，为什么？

8. trace 里最应该暴露哪些信息？

9. 分层 eval 的架构价值是什么？

10. 一份诚实的架构评价最后应该包含什么？

课程收束：你现在应该能评价什么

完成八课后，你应该能读懂并评价 CTI-RAG 的关键 runtime 架构：入口如何做 path selection，state 如何记录运行，工具边界如何把 proposal 变成 observation，ledger 如何成为证据权威，citation/grounding/eval 如何分层，supervisor 如何只做协调，最终架构如何用 tests、eval、trace 证明自己的 contract。

更重要的是，你现在有一套语言：control plane vs data plane、action vs observation、state vs memory、context vs prompt、ledger vs trace、validated plan vs legacy autonomous、citation validation vs grounding vs faithfulness、eval layer vs total score。以后读任何 Agentic RAG 项目，都可以先拿这些边界定位。
