Lesson 03 · Tool Boundary

Tool Calling Boundary：把模型建议变成可审计行动

第三课解决一个最容易被跳过的问题：LLM 说“我要调用工具”，并不等于系统已经安全、正确、可复现地执行了工具。Agentic RAG 的工具边界，就是把概率性的 action proposal 变成工程上可验证 observation 的地方。

先看全局：本课在地图哪里

前两课我们把入口和运行记录分开了：runtime harness 决定走哪条路，state/observation 记录一次 run 发生了什么。现在进入最关键的边界：模型可以提出动作，但 runtime 必须决定这个动作能不能被执行、怎么执行、执行结果如何进入 state 和 ledger。

Runtime/Harness

Tool validation、tool execution、budget、deadline、cache、parallel dispatch 都属于 runtime 控制面。它们不应该靠 prompt 的自觉完成。

LLM Call Points

Tool-calling LLM 只负责提出下一步 action。它可以建议 retrieve 或 graph_query，但它不是工具执行权威。

Evidence/Trust

工具结果能否成为证据，取决于 runtime 是否承认这次调用、ledger 是否记录了结构化结果和 provenance。

Cross-cutting

本课会反复用到三组边界：Action vs Observation、Trust Boundary、Deterministic vs Probabilistic。

本课核心胜利：你能看到一段 tool-calling 代码时，不会只问“模型能调哪些工具”，而会问“谁验证工具名和参数？谁拒绝越界调用？谁记录失败类型？谁保证重复调用、预算耗尽、deadline 到期时不会污染证据？”

学习目标：概念先于代码

1

能解释为什么 tool call 是模型的 action proposal，而不是已经发生的系统事实。

2

能区分 invalid、rejected、error、ok、no_action 这些 observation status 的工程含义。

3

能评价一个工具边界是否足够硬：schema validation、normalization、budget、deadline、cache、event、ledger delta 是否都在 runtime 侧完成。

代码在这里是辅助证据。你不需要先背 CTI-RAG 的函数名；你要先拿到一个判断框架：工具边界是 Agentic RAG 的信任边界，不是聊天协议的附属功能。

如果我是你，我会先问什么

如果现在还没有系统概念，我不会从“LangChain/OpenAI tool calling 怎么写”开始。我会先把动作链拆成三个问题：

问题概念答案为什么重要
模型输出的 tool call 是什么？ 它是 action proposal：模型建议系统去做某件事。 proposal 还没有经过系统授权。把它当事实，会让模型越过 runtime 边界。
runtime 在边界上做什么？ 验证工具名、参数、预算、deadline、重复调用和路径策略，然后执行或拒绝。 这些检查是确定性的工程约束，不能依赖模型自己遵守。
工具结果进入系统时是什么形态？ 应该是结构化 RuntimeObservation，再由 reducer 更新 state/ledger。 只有结构化 observation 才能审计、回放、测试和生成可靠 trace。

核心概念一：proposal 不等于 execution

Agentic RAG 里最危险的偷懒，是把模型输出的 tool call 当成系统已经完成的动作。模型说“调用 retrieve(query='APT29')”，只说明模型希望这样做；系统还需要回答：

runtime 问题如果不问，会发生什么
这个工具在 allowlist 里吗？ 模型可能调用不存在或不该暴露的工具。
参数是否符合 schema？ 坏参数会进入工具层，把 validation bug 伪装成 tool error。
参数是否需要 normalization？ 超长 query、空字符串、大小写差异会导致不可控行为。
是否超出 tool budget 或 deadline？ agent 可能无限探索，成本和延迟失控。
这个调用是否重复？ 同一工具和参数被反复执行，浪费预算，也会污染 trace。

读代码时的概念锚点：看到 tool_call 不要立刻理解成“工具结果”。先问它是否已经穿过 validation/admission/execution 三道门。没穿过之前，它只是模型 proposal。

核心概念二：五种 status 背后的工程含义

只用 success/failure 会把很多不同问题揉在一起。Agentic RAG 需要更细的状态，因为不同失败类型对应不同修复策略、重试策略和评估解释。

Status含义例子工程解释
ok 工具被 runtime 承认并成功执行。 facts_for_evidence 返回若干 fact。 可能产生 ledger delta，后续可以影响 sufficiency 和 synthesis。
invalid proposal 本身不合法。 缺少必填参数、未知参数、类型错误、未知工具。 工具不应该执行；这是边界 validation 的结果。
rejected proposal 可能合法，但 runtime policy 不允许执行。 工具预算耗尽、deadline 已到、graph coverage 后禁止 retrieve。 这是 admission/policy 拒绝，不应记成工具异常。
error 工具被允许执行，但执行层失败。 retriever 或 graph store 抛异常。 需要 error kind 和 event，方便重试与诊断。
no_action 模型这一轮没有提出工具动作。 模型直接输出文本或空动作。 这可能触发 stop policy 或 forced finish，但不是工具调用失败。

CTI-RAG 里的代码映射

现在再看项目代码。你读这些函数时，把它们当作概念边界的实现，而不是孤立函数。

代码位置它在概念上做什么读的时候重点问什么
runtime_harness.py::_validate_runtime_tool_args 工具 schema 和 allowlist 边界。 哪些工具可调？每个工具需要哪些参数？未知参数、缺失参数、坏类型如何被挡住？
runtime_harness.py::_normalize_runtime_tool_args 把模型参数收束到 runtime 可接受形态。 是否裁剪过长 query？是否让同一语义的参数更可缓存、可审计？
RuntimeTurnAdapter 把 CTI-RAG 的 retriever、graph、fact store 暴露成 runtime 工具集合。 工具描述是否只是给模型看的 affordance？真正执行是否仍经过 runtime？
_execute_action_proposal proposal 到 observation 的核心边界。 未知工具、坏参数、预算、deadline、重复调用、工具异常分别如何生成 observation？
_handle_tool_calls 把一轮可能多个工具调用 dispatch 成 observations。 并行执行时 observation id 是否唯一？state 更新是否仍可解释？
tests/unit/test_runtime_harness.py 把边界行为写成回归测试。 测试覆盖的是“模型输出了什么”，还是“runtime 如何承认、拒绝和记录”？

CTI-RAG 当前暴露的主要工具包括 resolve_entity、graph_outline、graph_query、facts_for_evidence、retrieve。注意：这些名字是项目事实；更重要的概念是，工具集合必须由 runtime 明确列出，并且每个工具都有参数、预算、结果和 ledger 影响的边界。

具体场景：模型想 retrieve，但 runtime 拒绝了

假设前几轮 graph 工具已经覆盖了问题需要的实体和关系，runtime policy 决定“graph coverage 足够后不要再走 prose retrieval”。这时模型又提出 retrieve。好的工具边界不会默默执行，也不会只在 prompt 里希望模型听话，而是产生一个明确 observation：

字段可能的值概念解释
Status rejected 工具名和参数可能没错，但 runtime policy 不允许当前路径继续 retrieve。
Error kind retrieve_suppressed_after_graph_coverage 这不是 retriever 坏了，而是控制策略做了拒绝。
Ledger delta 无新增 chunk/fact 没有执行工具，就不应该凭空生成证据。
Event rejected tool action trace 能解释为什么模型提议没有变成证据。

这个例子能帮你分清 “工具不可用”、“工具参数坏”、“工具执行失败” 和 “runtime 策略拒绝”。它们在用户体验上可能都表现为“没有拿到新证据”，但工程诊断完全不同。

常见误解

误解为什么不对更好的理解
“有 tool schema 就足够安全。” provider 侧 schema 只能约束模型输出形状，不能替代 runtime 的预算、deadline、cache、policy 和 ledger 管控。 schema 是输入门槛，runtime boundary 是执行权威。
“模型知道工具说明，所以会正确使用。” 工具说明只是给模型的 affordance。模型仍可能 hallucinate 工具名、给错参数、重复调用、过度探索。 prompt 指导概率行为，runtime 执行确定性约束。
“工具错误和参数错误都叫失败就行。” 参数错误要修 validation 或 prompt；工具错误要修服务、依赖或重试策略；budget 拒绝要调 policy。 failure taxonomy 是可诊断系统的基础。
“ToolMessage 就是 observation。” ToolMessage 是给模型看的协议文本，可能被截断或格式化。 observation 是系统内部结构化收据，ToolMessage 只是它的投影。

读代码时问什么

这不是口诀，而是一组审计问题。你每看到一个 tool-calling agent，都可以拿它检查边界是否足够硬。

审计问题你在找什么
工具集合在哪里声明？ 有没有明确 allowlist，而不是模型想调什么都能调。
参数在哪里验证？ 缺失、未知、类型、长度、枚举值是否在执行前被挡住。
runtime policy 在哪里生效？ 预算、deadline、路径策略、重复调用、并发限制是否由代码强制。
工具结果如何变成 observation？ 是否保留 status、error_kind、summary、structured payload、ledger delta。
证据如何进入 ledger？ 是否只让被承认的工具结果进入 ledger，拒绝/无效调用不会生成证据。
测试覆盖什么？ 有没有测未知工具、坏参数、预算耗尽、deadline、工具异常、并行 id、replay。

练习：至少先把边界看硬

1. 模型输出一个 tool call 后，最准确的说法是什么？

2. 缺少必填参数的工具调用应该是什么 status？

3. tool budget 用完后，模型又提出合法工具调用，应该如何理解？

4. 为什么不能把 ToolMessage.content 当作唯一状态源？

5. normalization 的价值是什么？

6. 重复工具调用为什么属于 runtime 要处理的问题？

7. 工具抛异常和参数 invalid 的区别是什么？

8. 一个被 rejected 的调用应该产生 ledger 证据吗？

9. 并行工具 dispatch 最需要守住什么？

10. 评价工具边界时，最关键的追问是什么？

本课小结

工具边界是 Agentic RAG 从“会聊天的模型”走向“可运行系统”的关键位置。模型提出 action proposal；runtime 验证、归一化、执行或拒绝；observation 记录边界事实；reducer 决定 state 和 ledger 如何变化。后面我们看 EvidenceLedger 时，要记住：ledger 不应该相信模型想做什么，只应该接收 runtime 承认后的证据结果。

下一课进入 EvidenceLedger：如果工具边界回答“什么动作真的发生了”，ledger 回答“哪些证据真的可被答案引用”。
