Lesson 06 · Supervisor

Supervisor：Admission 之后的协调层

第六课专门拆 supervisor。我们不把它讲成“一个更厉害的 agent”，而是讲成多分支 Agentic RAG 里的协调层：什么时候进入、它协调谁、它不能做什么、CTI-RAG 生产路径和 legacy debug 路径有什么区别。

先看全局：本课在地图哪里

前五课已经覆盖 single-agent gather loop：入口、state、工具边界、ledger、grounding。supervisor 出现的原因不是“所有问题都应该多 agent”，而是有些用户问题天然可以拆成独立 gather 分支，最后再统一 composition。

Multi-Agent/Supervisor

Supervisor、branch plan、worker、branch-local ledger、ledger merge、single composition 都在这一块。

Runtime/Harness

生产路径中，是否进入 supervisor 由 runtime admission 决定。supervisor 不应该自己决定简单问题是否要多分支。

Evidence Ledger

每个 worker 收集自己的 branch ledger，最终 merge 成 master ledger，供 citation guard 验证。

Grounding

Composer 负责最终文字，但不应该越过 merged ledger 编新证据。最终 citation 仍由 guard 处理。

本课核心胜利：你能把 supervisor 定位成“admission 之后、worker 之上、composer 之前的协调层”。它不负责判断所有问题是否该多分支，不直接检索，不直接写最终答案，也不替代 citation guard。

学习目标：先把角色边界立住

1

能解释 supervisor 为什么只适合 independent gatherable branches，而不适合所有复杂问题。

2

能区分生产路径的 validated branch plan 和 legacy autonomous supervisor debug/eval 路径。

3

能评价 supervisor 设计是否保持边界：dispatch worker、收 report、merge ledgers、call composer；不亲自检索、不亲自写最终答案、不验证 citations。

如果我是你，我会先问什么

你之前问过 supervisor 的定位，这里我们把问题拆到最小：

问题概念答案在 CTI-RAG 里的实际含义
supervisor 是入口路由器吗？ 不是。入口 admission 决定是否走 supervisor。 answer() 拥有 supervisor admission；生产路径传入 validated branch plan。
supervisor 是检索器吗？ 不是。它 dispatch worker，worker 执行 gather。 dispatch_worker 是子 agent 工具，不是直接 retrieval 工具。
supervisor 写最终答案吗？ 不应该。它把 branch reports 交给 Composer。 项目 ADR 明确 Composer 是 no-tool synthesis role。
supervisor 验证 citations 吗？ 不应该替代 citation guard。 最终答案仍通过 merged ledger 的 deterministic citation guard。

核心概念一：supervisor 不是“多 agent 魔法”

supervisor 适合的问题有一个共同特征：可以拆成若干相对独立的 gather 分支，并且最后需要统一 composition。比如：

问题类型是否适合 supervisor原因
比较两个 actor 的 technique overlap。 适合 APT29 分支和 Lazarus 分支可独立 gather，最后比较。
分别总结三个 malware family 的 capabilities。 适合 每个 family 可以独立收证据，最终汇总。
先识别实体，再根据实体结果决定下一步查什么。 不一定适合 这是 dependent chain，不是独立分支。single-agent loop 更自然。
一个简单 fact lookup。 不适合 多分支会增加成本和延迟，没有协调收益。
问题边界不清，需要探索性检索。 通常不适合直接 supervisor 没有清晰独立分支时，先走 single path 更安全。

判断句：supervisor 不是复杂度奖励机制；它是“多个独立证据采集任务需要统一合成”时的协调机制。

核心概念二：validated plan path vs legacy autonomous path

CTI-RAG 里尤其要分清两个路径：

路径定位谁决定分支什么时候用
Validated branch plan path 生产主路径。 runtime admission 先判断并传入 validated branch plan。 answer() 认为问题适合多分支时。
Legacy autonomous supervisor debug/eval/manual baseline。 supervisor 自己规划和循环。 用于对比、调试、评估，不应误读成生产默认。

这个区分能解释很多项目内看似矛盾的代码：你可能会看到 supervisor loop 里有自主规划逻辑，但 ADR 和生产路径已经把它限定为 legacy debug/eval。评价架构时，要问的是生产 API 走哪条路，而不是看到某段旧能力就认为它是主设计。

核心概念三：branch report 是摘要，branch ledger 才是证据

worker 完成后会交出 branch report。report 很重要，但它不是完整证据权威。完整证据在 branch-local ledger 中，最后 merge 成 master ledger。

对象保存什么用途
Branch report branch_id、sub_question、status、evidence_summary、key_entities、cited_ids、gaps、errors、stop_reason 等。 给 supervisor 和 Composer 一个 compact coordination view。
Branch-local ledger worker 实际收集到的 chunks/facts/outlines/actions。 保留完整证据，等待 merge 后供最终 citation guard 使用。
Merged master ledger 所有分支证据的去重合并结果。 最终答案的 evidence authority。

这个边界非常关键：如果 Composer 只凭 report 写答案、citation guard 又找不到 branch evidence，就会出现“报告里说有证据，但最终引用验证失败”的断裂。正确设计是 report 负责沟通，ledger 负责证据权威。

具体场景：什么时候不该进 supervisor

假设用户问：“FIN7 使用了哪些 persistence technique？”这看起来是 CTI 问题，但不一定需要 supervisor。single-agent loop 可以先 resolve entity，再 graph outline，再 facts_for_evidence 或 retrieve。它是顺序 gather，不是多个独立实体/分面同时收证。

判断点如果走 supervisor 的风险更合适的路径
只有一个 focus entity。 拆分会制造虚假分支，增加协调成本。 single-agent gather。
下一步依赖上一轮 entity resolution。 并行 worker 可能缺少共同 setup state。 顺序 action loop。
问题问一个 facet。 branch report 没有明显合成收益。 runtime 直接 gather 并 synthesize。

这能帮你理解 ADR 里为什么强调 fallback：parse 失败、low confidence、边界不清、dependent chains、simple questions、shared exploratory ledger 都应该避免盲目进入 supervisor。

具体场景：什么时候应该进 supervisor

再看一个适合的例子：“Compare APT29 and Lazarus Group in terms of credential access and lateral movement techniques.” 这个问题有两个实体、两个 facet，分支相对独立，最后需要比较。

BranchSub-questionWorker 做什么Composer 做什么
A APT29 credential access techniques 收集 APT29 + credential access 证据。 不用亲自查证据，只读 report 和 merged evidence context。
B APT29 lateral movement techniques 收集 APT29 + lateral movement 证据。 比较 APT29 内两个 facet。
C Lazarus credential access techniques 收集 Lazarus + credential access 证据。 比较两个 actor。
D Lazarus lateral movement techniques 收集 Lazarus + lateral movement 证据。 指出 shared/unique techniques 和 gaps。

supervisor 的价值在这里很清楚：它让每个 worker 聚焦独立证据采集，最后统一合成。它不是让多个 agent 各写一个答案再拼起来，而是让多个分支产出证据和报告，再由单一 Composer 写最终答案。

常见误解

误解为什么不对更好的理解
“supervisor 越智能越好，最好自己规划、检索、写答案。” 这样会把 admission、gather、composition、citation guard 混成一个大黑盒。 supervisor 应该窄：协调 worker，保持边界清晰。
“复杂问题都走 supervisor。” 复杂问题可能是依赖链或探索型任务，不一定能并行分支。 只有 independent gatherable branches 才适合。
“branch report 就是证据。” report 是摘要，可能省略细节和 provenance。 branch ledger 才保存完整证据，最终要 merge。
“Composer 可以顺手补证据。” Composer 如果再调用工具或引入新事实，会绕过 branch ledger 和 citation guard 设计。 Composer 是 no-tool synthesis role。
“legacy autonomous supervisor 就是当前生产设计。” 项目保留 legacy path 用于 debug/eval/manual baseline。 评价生产架构要看 validated branch plan path。

本课小结

Supervisor 的概念定位是多分支协调层，不是更大的万能 agent。生产路径应该由 runtime admission 决定是否进入 supervisor，并提供 validated branch plan；supervisor dispatch gather-only workers，收 compact reports，合并 branch ledgers，再调用 no-tool Composer 写最终答案。最终 citation 仍由 merged ledger 的 deterministic guard 验证。下一课我们进入 eval：如何分层评价检索、证据、答案、faithfulness、citation、成本和回归。
