Core Terms

核心术语表

这份术语表是读 CTI-RAG Agentic RAG 代码时的速查页。每个术语都服务于一个边界判断：它属于控制、状态、工具、证据、可信度、supervisor、eval，还是架构评价。

第一组：控制平面

Runtime harness

模型外部的运行时控制层：理解输入、选择路径、验证工具、更新 state、执行 stop policy、记录 trace、组装最终答案。

Control plane

决定下一步能不能发生的代码：routing、validation、budgets、deadline、stop reason、fallback、trace events。

Runtime query understanding

把用户问题变成 standalone task、retrieval queries、entities、constraints 和可选 decomposition proposal。

Supervisor admission

runtime harness 对 branch plan 的保守裁决：只有独立、可并行、需要合成的分支才进入 supervisor。

Stop policy

决定继续 gather 还是 synthesize 的规则集合，依赖 sufficiency、进展、预算、时间、工具次数和 provider/tool failures。

RuntimeDeps

可复用服务和 provider policy，例如 settings、retriever、fact store、models、judge、composer。不要放 per-run reasoning state。

第二组：状态与工具边界

Runtime state

一次运行里的控制变量，例如 iteration、tokens、new evidence、sufficiency、stop reason、observations、events。

Action proposal

模型提出的工具调用意图。它还不是执行事实，必须经过 runtime validation 和 admission。

Tool boundary

把 probabilistic model proposal 变成 deterministic runtime observation 的信任边界。

Tool validation

代码级检查工具名、必填参数、未知参数、类型、长度、预算、deadline、重复调用和路径 policy。

Observation

工具边界返回的结构化结果，包括 status、error、summary、structured payload、ledger delta 和 model-visible content。

Observation status

ok 成功执行；invalid proposal 不合法；rejected policy 拒绝；error 执行层失败；no_action 模型没有动作。

RuntimeEvent

从 observation 派生的观测事件，用于 trace、计数、debug 和 eval 分析，不是完整证据仓库。

Reducer

把 observation 确定性合并进 state 和 ledger 的逻辑。它让状态更新可回放、可测试、可审计。

Working-set context

每轮从 state/ledger 重新渲染给模型看的工作视图，不是 durable state 本身。

Setup progress

不新增 citable evidence、但为后续 gather 做准备的进展，例如 entity resolution 或 graph outline。

第三组：证据与可信度

Evidence ledger

本次运行的证据权威：chunks、facts、outlines、actions、conflicts 和真实可引用 ID 集合。

Per-run evidence authority

答案能引用什么，以本次 run 收集进 ledger 的证据为准，不以全局知识库或模型记忆为准。

Provenance

证据来源：source、chunk ID、fact ID、document metadata、support edge 和可信度信号。

Citation

答案中显式出现的 chunk/fact ID 引用。它是证据指针，不自动等于 claim 被支持。

Citation validation

把模型写出的 citation IDs 与 ledger 的真实 ID 集合求交；这是确定性 guard。

Grounding

答案 claim 是否能落回收集到的 evidence，而不是来自模型自由记忆。

Faithfulness

答案是否忠实表达证据，没有夸大、改写、拼接出证据不支持的结论。

Sufficiency

已有证据是否足够覆盖用户问题的关键 facet。它是 gather stop 的核心输入之一。

Deterministic guard

用代码执行的确定性检查，例如 citation ID 是否存在、工具参数是否合法。

LLM-as-judge

用模型评估语义质量或 coverage 的概率性判断，适合 claim support、faithfulness、sufficiency 等较难形式化的问题。

第四组：Supervisor

Branch plan

一组经过 admission 的独立 sub-questions，适合并行 gather，并在最后统一 composition。

Supervisor

已放行多分支任务的协调者：调度 gather-only workers，汇总 branch reports，触发 Composer。

Worker

围绕一个 branch 收集证据的分支 agent，产出 branch-local ledger 和 compact branch report。

Branch report

分支协调摘要：status、sub-question、evidence summary、cited ids、gaps、errors、counts、stop reason。

Branch-local ledger

每个 worker 独立收集的证据账本，最后合并成 master ledger。

Ledger merge

把分支 ledger 确定性合并成 master ledger，供最终 citation validation 使用。

Composer

无工具的最终合成角色，只从 branch reports 和 accepted evidence context 写一个答案。

Validated plan path

生产路径：runtime admission 已经验证 branch plan，supervisor 只负责协调执行。

Legacy autonomous supervisor

用于 debug/eval/manual baseline 的自主 supervisor 路径，不应误读为生产默认。

第五组：Evaluation 与架构评价

Retrieval eval

测 retriever 是否返回 expected chunks、sources 或 ATT&CK IDs，常见指标包括 hit@k、MRR、NDCG。

Gathered evidence eval

测 agent 实际收集到了什么证据，而不是 retriever 理论上能搜到什么。

Answer eval

测最终答案的正确性、完整性、相关性、可读性和任务满足程度。

Faithfulness eval

测答案是否被 retrieved/ledger evidence 支持。它不等同于外部世界事实正确性。

Citation eval

测 citations 是否存在、是否为有效 ledger IDs、是否与 claim 支撑关系匹配。

Regression test

防止 runtime、tool、ledger、citation 或 eval 行为在重构中悄悄漂移的可重复测试。

Golden set

一组固定问题和 expected evidence/answers，用于比较模型、代码、prompt、retriever 改动前后的表现。

Runtime contract

系统对调用方和维护者承诺的行为：入口、输出 shape、trace、fallback reason、stop reason、citation behavior。

Architecture review

把 design intent、runtime contract、code evidence、tests/eval evidence 和 residual risks 分开评价。

横切边界

边界一句话
State vs Memorystate 是当前 run 的控制变量；memory 是被选择进 context 的信息来源。
Context vs Promptcontext 是选入模型调用的材料；prompt 是最终序列化输入。
Action vs Observationaction 是系统尝试或模型 proposal；observation 是边界返回的结构化事实。
Plan vs Traceplan 是预期路线；trace 是实际执行记录。
Ledger vs Traceledger 是证据权威；trace 是运行解释和观测记录。
Control Plane vs Data Planecontrol plane 决定能不能做；data plane 提供证据内容。
